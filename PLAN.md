# Экономия действий — план модуля

Модуль для **Foundry VTT 14.367 + D&D5e 5.3.3 + Midi-QOL 14.0.12**: счётчики основного
действия, бонусного действия, реакции, свободного действия и концентрации на листе персонажа.

Статус: версия 0.1.0 написана и подготовлена к публикации на GitHub и в реестре Foundry
(`LICENSE`, `CHANGELOG.md`, `.github/workflows/release.yml`, английский `README.md`).
Идентификатор `action-economy` в реестре Foundry свободен — проверено 2026-09-17.
В игре проверялась автономная версия из `tools/standalone-macro.js`; сам модуль ещё не ставился. Разметка листа, порядок хуков
и работа концентрации **проверены в мире пользователя** макросами из `tools/`
(отчёты от 2026-09-17). Логика расчётов покрыта `tests/smoke-test.cjs`.
Инструкция пользователя — в [README.md](./README.md).

## 1. Поиск готового решения

Точного совпадения нет. Что найдено:

| Модуль | Что умеет | Почему не подходит |
| --- | --- | --- |
| [D&D 5e HUD to Rule Them All](https://github.com/Domiknonf/dnd5e-hud-to-rule-them-all) | пулы действий/бонусных/реакций/легендарных, ручная правка кликом, оверрайды пулов, видимость по владению | заявлена совместимость Foundry **v13** и dnd5e 5.x, не v14/6.x; формат — большой BG3-хотбар вместо компактного блока в шапке листа; нет свободного действия и концентрации |
| [Action Tracker](https://foundryvtt.com/packages/action-tracker) | кнопки отметок в Token HUD и трекере боя, проверен для Foundry 12–14 | чисто ручные отметки: нет автосписания по использованию Activity, нет концентрации и свободных действий, нет увеличения пулов эффектами |
| [Combat Chat Tracking D&D5e](https://foundryvtt.com/packages/combat-chat-tracking) | отметки действия/бонусного/реакции в карточке хода | учёт живёт в чате, не на листе; без автоматики и модификаторов |
| [D&D 5e Action Sheet](https://foundryvtt.com/packages/sidebar-traits) | группировка способностей по типу активации | это раскладка списка способностей, а не счётчики ресурсов |
| [Concentration Notifier](https://foundryvtt.com/packages/concentrationnotifier) | напоминания о концентрации | заброшен (проверен для v9–11); в dnd5e концентрация давно штатная |

Вывод: пишем свой модуль. Концентрацию при этом **не реализуем заново** — она уже есть
в системе (см. ниже), модуль только показывает её в общем ряду и даёт снять кликом.

## 2. Проверенные факты API

Источник: исходники dnd5e тега `release-5.3.3` (именно эта версия стоит у пользователя).
Отдельно сверено с master 6.0.3 — в нужных нам местах различий нет, модуль переживёт
обновление системы.

- Типы активации: `CONFIG.DND5E.activityActivationTypes` — `action`, `bonus`, `reaction`,
  `minute`, `hour`, `day`, `longRest`, `shortRest`, `encounter`, `turnStart`, `turnEnd`,
  `legendary`, `mythic`, `lair`, `crew`, `special`.
  **Отдельного «свободного действия» в системе нет** — его нужно вводить своим правилом (см. 4.3).
- Хуки использования (`module/documents/activity/mixin.mjs`):
  - `dnd5e.preUseActivity(activity, usageConfig, dialogConfig, messageConfig)` — можно вернуть `false` и отменить использование;
  - `dnd5e.postUseActivity(activity, usageConfig, results)` — использование уже состоялось;
  - `dnd5e.preActivityConsumption` / `dnd5e.activityConsumption` / `dnd5e.postActivityConsumption`.
- Концентрация уже реализована системой (`module/documents/actor/actor.mjs`):
  - `actor.concentration` → `{ items: Set<Item5e>, effects: Set<ActiveEffect5e> }`;
  - предел — `actor.system.attributes.concentration.limit` (штатное поле, поднимается обычным Active Effect);
  - хуки `dnd5e.preBeginConcentrating`, `dnd5e.beginConcentrating`, `dnd5e.preEndConcentration`, `dnd5e.endConcentration`.
- Лист персонажа — ApplicationV2 `CharacterActorSheet` (**подтверждено в мире пользователя**),
  корень листа: `application sheet dnd5e2 actor standard-form character vertical-tabs interactable cs`,
  `sheet.element` возвращает `HTMLElement`. Шапка — часть `header`,
  шаблон `systems/dnd5e/templates/actors/character-header.hbs`.
  Разметка (**подтверждена макросом, совпадает с исходником**):

  ```
  header.sheet-header
    div.left                     имя и класс
    div.right
      div.level-badge.badge
      button.inspiration
      div                        (без класса)
        div.sheet-header-buttons    button.short-rest + button.long-rest
        div.xp-label
        div.xp-bar
  ```

  Зелёная рамка со скриншота — свободное место слева от кнопок отдыха, то есть **внутри
  ряда `.sheet-header-buttons`**.
- Схемы данных dnd5e строгие: `MappingField` с `initialKeysOnly` выбрасывает чужие ключи
  ([misthero/dnd5e-custom-skills#61](https://github.com/misthero/dnd5e-custom-skills/issues/61)).
  Отсюда правило: **не добавлять свои поля в `system`**, состояние держать во флагах модуля.

## 3. Данные и источники истины

Идентификатор модуля: `action-economy`.

| Ресурс | Текущее значение | Максимум |
| --- | --- | --- |
| Основное действие | флаг `flags.action-economy.spent.action` | база + эффекты + оверрайд |
| Бонусное действие | `…spent.bonus` | то же |
| Реакция | `…spent.reaction` | то же |
| Свободное действие | `…spent.free` | то же |
| Концентрация | `actor.concentration.effects.size` (**штатное**) | `actor.system.attributes.concentration.limit` (**штатное**) |

- Хранится только **число потраченного** по четырём пулам плюс метка раунда и боя, чтобы
  отличать устаревшее состояние. Концентрация своего состояния не заводит — правило
  «не дублировать состояние, уже представленное системой» из
  [библиотеки методов](../feature-notes/methods.md).
- Область действия — **только листы персонажей игроков** (`actor.type === "character"`).
  На NPC модуль не работает: ни виджета, ни списания, ни проверок. Поэтому сокет не нужен —
  флаги пишет владелец актёра, а у мастера права есть на всё.

### Как считается максимум

1. База — 1 у каждого из четырёх пулов.
2. Поверх базы модуль **сам** перебирает `actor.appliedEffects` и применяет изменения
   с ключами `flags.action-economy.max.action|bonus|reaction|free` в порядке приоритета,
   с режимами Add, Multiply, Upgrade, Downgrade, Override.
3. Жёсткий оверрайд `flags.action-economy.override.<пул>` — приоритетнее всего.
4. Концентрация в этой схеме не участвует: её предел поднимается штатным эффектом
   на `system.attributes.concentration.limit`.

**Почему считаем сами, а не полагаемся на штатное применение эффекта к флагу.**
Рассматривался вариант засеять `flags.action-economy.max` в `Actor.prototype.prepareBaseData`
через libWrapper и отдать всё ядру. Отказались: поле `flags` — это `ObjectField`, и
подготовленный объект остаётся той же ссылкой, что и `_source.flags`, поэтому запись
производного значения загрязняет исходные данные актёра и попадает в экспорт.
Объявить поле через схему тоже нельзя — модели данных dnd5e строгие
([misthero#61](https://github.com/misthero/dnd5e-custom-skills/issues/61)).
Свой подсчёт не трогает данные вообще, не требует libWrapper и даёт предсказуемый
результат независимо от версии ядра. Отключённые и подавленные эффекты в
`appliedEffects` не попадают, так что это учитывается само.

### Готовые эффекты

Создаются макросом `tools/create-effects.js` как особенности в папке предметов мира
(компендиум-пак руками не собрать — это LevelDB). Все — Active Effect:

- «Дополнительное действие» — `flags.action-economy.max.action`, режим Add, +1;
- «Дополнительное бонусное действие» — `…max.bonus`, Add, +1;
- «Дополнительная реакция» — `…max.reaction`, Add, +1;
- «Дополнительное свободное действие» — `…max.free`, Add, +1;
- «Дополнительная концентрация» — `system.attributes.concentration.limit`, Add, +1 (штатный ключ).

## 4. Поведение

### 4.1 Автоматическое списание

- `dnd5e.preUseActivity` → определяем пул по `activity.activation.type`
  (`action` → основное, `bonus` → бонусное, `reaction` → реакция) и проверяем остаток.
- Фактическое списание — в `dnd5e.postUseActivity`, чтобы отменённый диалог не съедал ресурс.
- Концентрация списывается сама: её ведёт система, модуль только перерисовывает виджет
  по `dnd5e.beginConcentrating` и `dnd5e.endConcentration`.

**Подтверждено игровым тестом (Midi-QOL 14.0.12, оружие и заговор):** хуки dnd5e доходят,
Midi их не глушит. Фактический порядок:

```
+0 мс   midi-qol.preItemRoll
+8 мс   dnd5e.preUseActivity
+8 мс   dnd5e.preActivityConsumption → activityConsumption → postActivityConsumption
+16 мс  dnd5e.preCreateUsageMessage
+72 мс  dnd5e.postCreateUsageMessage → dnd5e.postUseActivity
+2.5 с  midi-qol.AttackRollComplete → DamageRollComplete → RollComplete
```

То есть `postUseActivity` приходит **до** броска атаки, а не после — ресурс спишется сразу
при использовании, и это правильно. Резервные midi-хуки не нужны.

Ещё из теста: у переключателя «Стеклянная пушка» активация `special`. Такие активности
не должны стоить ничего — подтверждает правило «считаем только `action`, `bonus`, `reaction`».

**Концентрация подтверждена отдельным прогоном** («Безудержный смех Таши»):
концентрацию ставит **система**, а не Midi, `dnd5e.beginConcentrating` приходит через
1.97 с после `preUseActivity` и **до** `postUseActivity`, `dnd5e.endConcentration` —
при снятии. Модулю достаточно читать `actor.concentration`.

Там же видно, что между `preUseActivity` и расходом проходит 1.6 с — это диалог выбора
ячейки заклинания. То есть наша проверка ресурса случается **до** диалога, и при отмене
диалог даже не появится.

### 4.2 Что происходит при нехватке ресурса

Всплывашка плюс вопрос «Основное действие уже потрачено. Всё равно использовать?»
с кнопками «Использовать» и «Отмена».

**Техническая тонкость:** `Hooks.call` синхронный, дождаться ответа диалога прямо
в `dnd5e.preUseActivity` нельзя. Схема такая:

1. в `preUseActivity` при нехватке ресурса вернуть `false` — использование отменяется;
2. показать диалог подтверждения;
3. при ответе «Использовать» повторно вызвать `activity.use(usageConfig, dialogConfig, messageConfig)`
   теми же объектами конфигурации, пометив вызов как подтверждённый (метка в
   `usageConfig` либо `WeakSet` активностей), чтобы проверка второй раз не сработала;
4. при отмене ничего не делать.

**Риск, выявленный тестом:** `midi-qol.preItemRoll` срабатывает за 8 мс **до**
`dnd5e.preUseActivity`, значит на момент нашей отмены workflow Midi уже создан. Нужно
проверить, что отменённый workflow не зависает и не ломает следующий бросок. Если ломает —
переносим проверку в `midi-qol.preItemRoll`: он идёт первым и Midi штатно поддерживает
отмену возвратом `false`.

### 4.3 Свободное действие

Автоматики нет. Свободное действие **тратится и восстанавливается только вручную**
кликом по точке. Никаких флагов на предметах и правил по типу активации.

### 4.4 Ручное управление

Клик по точке пула переключает «потрачено ↔ восстановлено» — всегда, независимо от режима.
Клик по точке концентрации предлагает снять соответствующий эффект концентрации.

### 4.5 Сброс

- Начало хода актёра — сброс основного, бонусного, свободного и реакции
  (реакция по правилам восстанавливается в начале своего хода).
- Конец боя (`deleteCombat`) — сброс всех.
- Вне боя счётчики не списываются автоматически (настройка), сброс — кликом.
- **Проверить:** фактическое имя хука смены хода в Foundry 14 (`combatTurnChange` против
  `updateCombat`) и поведение при перемотке раундов назад.

## 5. Интерфейс

- Виджет вставляется первым элементом внутрь `.sheet-header-buttons` — это готовый ряд,
  в котором лежат кнопки отдыха, наш блок встанет слева от них, ровно как на скриншоте.
  Запасная точка, если ряд не найден: `header.sheet-header .right > div` перед кнопками.
- Хук отрисовки: **`renderActorSheetV2`**, то есть имя базового класса ядра, а не
  `renderCharacterActorSheet`. ApplicationV2 вызывает хуки для всей цепочки классов,
  а имена классов D&D5e система уже переименовывала (`ActorSheet5eCharacter2` →
  `CharacterActorSheet`), так что привязка к ним ломается на каждом переезде.
  Пункт меню — по той же причине `getHeaderControlsActorSheetV2`.
  Оба имени подтверждены диагностикой на живом листе.
  Вторым аргументом приходит `HTMLElement`, не jQuery.
- Рисуем только для `actor.type === "character"`.
- Вставка идемпотентная: перед добавлением удалять прежний блок по своему CSS-классу
  (подтверждённая практика из библиотеки методов — иначе частичная перерисовка ApplicationV2
  наплодит дубликаты).
- Строка ресурса — иконка плюс ряд точек: точек столько, сколько максимум, потраченные чёрные.
  Иконки и цвета как на эталонном скриншоте: зелёный круг — основное, рыжий треугольник —
  бонусное, синяя капля — свободное, круговая стрелка — реакция, розовая звезда — концентрация.
- Обработчик кликов — делегированный, на корне виджета.
- Скрытые настройкой ресурсы просто не рисуются.

## 6. Настройки

| Настройка | Область | Смысл |
| --- | --- | --- |
| Ручной режим | мир | автоматика ничего не списывает, остаются только клики |
| Отключить уведомления | мир | не спрашивать подтверждение и не слать всплывашки **и снять обработчик**, чтобы не держать лишнюю нагрузку |
| Показывать ресурсы игрокам | мир | набор флажков по каждому из пяти ресурсов: какие строки вообще есть в игре |
| Показывать виджет у меня | клиент | личный выключатель, **по умолчанию выключен** |

Показ виджета решается двумя независимыми выключателями в меню листа (три точки), хватает
любого: личный (клиентская настройка, действует на всех листах у этого пользователя) и
пер-персонажный (флаг `flags.action-economy.enabled`, действует на этом листе у всех).
По умолчанию оба выключены, то есть виджета не видно ни у кого, пока его не включат.
| База пулов | мир | стартовые максимумы (по умолчанию 1/1/1/1) |
| Вести учёт вне боя | мир | списывать ли ресурсы, когда боя нет |

Жёсткий оверрайд количества — в меню листа персонажа (три точки в шапке), пункт
«Экономия действий»: диалог с числом по каждому пулу и кнопкой «Сбросить к расчётному».
**Проверить:** фактическое имя хука на добавление пункта в меню ApplicationV2 в Foundry 14;
запасной вариант — правый клик по виджету.

Обработчики регистрируются по настройкам: при выключенной автоматике и уведомлениях
хуки не вешаются вовсе.

## 9. Решения пользователя и открытые вопросы

Решено:

- свободное действие — **только вручную**, автоматики нет (4.3);
- NPC не нужны, **только листы персонажей игроков** (раздел 3);
- при нехватке ресурса — всплывашка с вопросом «ты уверен?» и возможностью продолжить (4.2).

## 10. Аудит совместимости (2026-09-17)

Вся поверхность взаимодействия модуля с миром — шесть хуков, восемь настроек в своём
пространстве имён, один узел в DOM шапки и запись в свои флаги:

| Что делает модуль | Где |
| --- | --- |
| Слушает `renderActorSheetV2`, `getHeaderControlsActorSheetV2` | отрисовка и меню листа |
| Слушает `dnd5e.preUseActivity`, `dnd5e.postUseActivity` | списание ресурсов |
| Слушает `updateCombat`, `deleteCombat` | сброс |
| Пишет `flags.action-economy.spent.*` и `override.*` | своё пространство имён |
| Пишет `system.attributes.concentration.limit` | только по явному действию пользователя в диалоге |
| Регистрирует восемь настроек | пространство имён `action-economy` |

Чего модуль **не** делает: не патчит прототипы, не использует libWrapper, не меняет
`CONFIG`, не трогает модели данных, не открывает сокеты, не регистрирует свои типы
документов и листы, не пишет в чужие флаги. Поэтому классических конфликтов
«двое обернули один метод» у него быть не может.

### Что может сломаться

1. **Вёрстка шапки листа.** Единственная жёсткая привязка к разметке —
   `.sheet-header-buttons` и `header.sheet-header .right`. Если D&D5e её переделает,
   виджет не найдёт место: одно предупреждение в журнале, остальное продолжает работать.
   На сторонних листах (Tidy5e и подобные) виджета не будет, уведомление не показывается.
2. **Отмена использования при нехватке ресурса.** `midi-qol.preItemRoll` срабатывает
   раньше нашей проверки, значит workflow Midi к моменту отмены уже создан. Не проверено.
   Запасной выход — настройка «Только уведомление».
3. **Двойное списание, если использование выполняется на двух клиентах.** Модуль
   списывает там, где сработал `postUseActivity`, и условие — владение актёром, а мастер
   владеет всеми. Если Midi когда-нибудь повторит `activity.use` на стороне мастера,
   спишется дважды. Проверяется прогоном `probe-activity-hooks.js` одновременно у игрока
   и у мастера, пока игрок бьёт.
4. **«Дополнительная атака»** тратит действие на каждое использование активности атаки.
   Это поведение по устройству, лечится кликом по точке.
